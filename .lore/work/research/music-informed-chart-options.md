# Music-informed four-lane chart options

## Key findings

- Keep the existing aubio onset workflow as the baseline, but do not mistake its practical appeal for an evidenced reason it was originally selected. Its official project documents a small C library with no required dependencies (since 0.4.0), onset/beat/pitch features, and an old commit history; that supports a lightweight/dependency rationale, not a claim that it was chosen to ship quickly. The local draft already records that current lane assignment cycles a fixed pattern after onset detection; its proposed four spectral bands are explicitly evidence-based band mapping, not pitch or instrument recognition.
- `aubio` and `librosa` are not direct winners/losers. aubio is a lower-level C analysis library/CLI with causal onset, beat, and pitch algorithms and minimal mandatory dependencies. librosa is a Python analysis toolkit with broad spectral, chroma, onset and beat building blocks. Neither fact establishes chart quality, CPU throughput on these 29 songs, nor superior lane choreography. No local-song benchmarks or listening were run for this memo.
- For a four-key game where the player is a performer, a stable pitch-contour-to-lane mapping is musically more legible in principle than arbitrary spectral-band or instrument-class mapping: rising/falling melody can correspond to movement across ordered keys. However, single predominant melody is often not reliably recoverable from full mixes. A four-band spectral map is inexpensive and transparent but means brightness/energy region, not melodic pitch; a player is unlikely to infer instrument identity from it. More importantly, no mapping alone guarantees fun: fixed motifs, readable patterns, note density, and ergonomic finger transitions matter.
- Chroma (pitch class) is not register: its usual 12 bins fold octaves together. It can express harmonic/key/color changes but cannot by itself assign a note to a low-to-high lane in register order. Literal pitch-to-lane bins can chatter, collapse into a narrow range, or mismatch accompaniment; use smoothed, song-relative pitch contour/register and motif-preserving variation only if pitch evidence proves stable.
- Practical recommendation: evaluate onset timing separately from lane choreography. First compare the inexpensive interpretable candidate (multi-band onset evidence and/or smoothed tonal contour) against current cyclic lanes; then, only if actual song cases justify it, test an optional predominant-melody extractor. Keep Basic Pitch and source separation outside the default budget path: their potential value does not establish broad-mix performance or CPU suitability here.

## Existing draft context and its boundary

The draft proposes an opt-in offline CPU analyzer and states current generation detects aubio onset times, filters them, then cycles a configured lane pattern. Its proposed librosa pipeline computes multi-band spectral changes, optionally applies HPSS, and maps strongest of four ordered bands to a preferred lane. It explicitly says this is *not* pitch or instrument identity and acknowledges arbitrary-feeling band mapping as a risk. It also treats Easy/Normal/Hard as nested event subsets, which preserves note timestamps and lane identity while thinning. This is a useful auditable baseline, but it addresses changing timbral/spectral energy more directly than the player-facing question of making lanes represent melodic pitch.

The design question is not “which library wins?” but “which audible feature should control note placement and which should control lane patterning?” Separate event timing (onsets/beat evidence) from event identity/choreography (melodic contour, tonal/register changes, or stable pattern rules). Avoid coupling a weak pitch estimate to every hit.

### Comparison and judgment

**aubio vs librosa.** aubio was a sensible minimal dependency for the existing task—onset extraction—and has official support for several algorithms. The evidence for “quick-to-market” is insufficient: a repository commit may show the chronology of adding aubio, but not the author’s motive. The current draft’s pivot to librosa is justified if multi-band feature prototyping and visualization/analysis primitives are wanted, not because librosa has demonstrated better events or chart feel. A small aubio C tool plus custom lightweight features is also conceptually possible, but Python/FFmpeg already appear in the existing workflow and actual integration burden must be measured.

**Pitch-source hierarchy.** A pitch estimate from one frame can represent a harmonic, bass note, chord component, or noise transient rather than the lead. `piptrack` returns multiple spectral peaks and is not a melody selector; aubio’s single F0 methods are most defensible on monophonic/near-monophonic material. Essentia’s own page specifically describes its PitchMelodia implementation as monophonic-adapted. Basic Pitch can transcribe multiple simultaneous notes, but it does not promise which notes comprise the perceptual lead. In all cases, require confidence/voicing and temporal continuity, reject likely octave jumps, and retain a “no reliable pitch” state rather than forcing a lane. A melody extractor is a candidate input, not ground truth.

**Source separation.** Separation can create analysis targets when vocals or bass clearly carry the line, but choosing stems by genre is not robust for all 29 mixed AI-owned songs. It adds substantial model/runtime/dependency/storage footprint and artifacts. Do not make it required under the offline, budget-conscious constraints. Test only songs where direct-mix tonal evidence is demonstrably unusable and where the selected stem is musically appropriate.

## Player-facing lane semantics

The four keys read by players as four ordered actions; the player is a performer whose inputs should evoke musical expression and story, rather than an instrument-per-lane simulation. Instrument-family assignment (“kick always left, vocal always right,” etc.) is especially risky: source identity may be wrong in the mix, and changing voices between notes can make the lanes feel disconnected. It can also map non-pitched events to invented identities. Do not label or narratively imply that lanes are instruments unless the game has explicit keysounds and validated player understanding.

Pitch contour is a stronger *semantic hypothesis*, not a proven best design. Four keyboard positions can encode relative low-to-high movement. Candidate approaches:

1. **Relative, smoothed contour:** quantize local/phrase-relative melody register or pitch movement to ordered lanes; use hysteresis and a neutral/unknown path. This can make a rising melody visibly/physically rise and a falling contour descend. Calibrate ranges per phrase/song so transposition and register differences do not pin most notes to one lane. Preserve meaningful repeated notes and motif shape, rather than mapping every semitone or octave literally.
2. **Pitch-class/chroma mapping:** use tonal/harmonic change to color a phrase or choose a small number of stable lane states, not direct register order; chroma folds octaves, so a chroma row is not “low lane to high lane.” Its strengths are relative harmonic context and repeated pitch classes, but chord mixtures can activate many bins.
3. **Spectral-band mapping:** strongest positive flux among low/mid/high bands can yield transparent, reproducible lane evidence at low algorithmic complexity. Interpret it only as spectral region/brightness/transient evidence. It can assign drum attacks, broadband noise, or harmonics to a band; it does not tell the player that an instrument or pitch occurred. Strongly changing lanes on every band winner can feel arbitrary.
4. **Stable pattern baseline:** retain the current repeating pattern as a meaningful baseline. In some songs, a simple repeated lane can express a recurring beat/motif and be more playable than literal feature-following. A source-informed option should not be presumed superior merely because it has more features.

Across these, use pitch as a *directional cue* or phrase-level motif input, not an unquestioned note-to-lane classifier. Keep continuity, repeated motives, and bounded variation. Let rhythm/event selection carry onset and beat accents; let a separate patterning stage organize hand shapes and motifs. Do not make difficulty simply equal to more literal transcription: increase density/complexity gradually while preserving motif identity and ergonomic patterns. Remove notes from a canonical sequence only if that yields coherent Easy/Normal/Hard subsets; thinning alone can leave awkward gaps or destroy a phrase, so review actual results.

## Runtime, dependency, license, and budget notes

- **aubio:** official site says C and no required dependencies since 0.4.0; optional media/FFT libraries are possible. GPL is stated by the official project; verify exact release/linked components before redistribution. Strong practical low-footprint candidate for onset/beat baseline. No measured runtime for this project.
- **librosa:** ISC. Official install instructions say PyPI installation resolves required dependencies. It is a Python package and commonly sits on NumPy/SciPy/Numba and audio decoding dependencies; confirm exact pinned version/dependency closure in a controlled environment. Feature computations are offline and CPU-compatible in principle; no memory/time numbers for full tracks are established here.
- **Essentia:** C++ core, Python/JS bindings, streaming API, stated memory efficiency advantage; AGPLv3 or proprietary license on request. Its performance characterization comes from maintainers, not a benchmark on this collection. License compatibility warrants legal review before product distribution.
- **Basic Pitch:** Apache-2.0 code. Official README documents TensorFlow/CoreML/TFLite/ONNX options; its installation uses a runtime selected by platform and Python version. It requires pretrained model assets and extra dependencies beyond a conventional DSP pipeline. No required GPU/training is shown; explicitly benchmark CPU runtime and model download/size in a disposable environment before considering use. This research did not install it.
- **Demucs:** MIT code, but pretrained models are separately distributed/downloaded; repo describes CPU operation and roughly 1.5× track-duration processing. Repository says it is no longer maintained. Not a budget-neutral default and not a guarantee of useful lead stems.
- **Overall:** one-time offline analysis of 29 songs may tolerate more compute than runtime gameplay, but project requirement is ordinary CPU and low budget. Record elapsed wall-clock, peak resident memory, install/dependency size, model download size, and failures on the actual 29 files. Costs are presently unknown. A paid API or mandatory GPU is unnecessary to test any of the deterministic DSP options.

## Evaluation plan (must use the actual songs)

Do not decide from algorithm APIs or aggregate onset/pitch metrics alone. Use a small, stratified pilot (representative genres; vocal, instrumental, dense, sparse, percussive, and ambiguous melody) before batch-evaluating all 29. Run at least these isolated alternatives with the same timing events and density budget: current cyclic pattern; fixed spectral-band mapping; smoothed pitch contour if confidence permits; and a stable pattern/contour hybrid. Test raw candidate features on labeled short passages by human listening, not just visual plots.

For each song, record:

- **Timing:** onset/beat alignment against manually reviewed audible target events; early/late errors and missed/extra notes, with tolerance appropriate to the game’s judgment windows. Keep onset detection results separate from pitch/lane outcomes.
- **Pitch evidence:** valid voiced coverage, confidence calibration, octave errors/jumps, melody-vs-accompaniment selections and cases with no reliable lead. Manually annotate a small excerpt when possible. Chroma coverage is not pitch-register accuracy.
- **Musical fit and motif:** whether lane direction tracks heard melodic contour; repeated phrases return to recognizable patterns; lane changes correspond to a meaningful audible event; no arbitrary lane flicker. Compare music and chart synchronized; listen to chart rendered as key sounds only if that rendering exists and is permitted.
- **Player feel/ergonomics:** blind or counterbalanced playtest/inspection of representative charts at intended speeds and difficulty. Record perceived readability, playability, hand strain/awkward alternations, repeated-lane fatigue, abrupt cross-hand travel, predictability and musical satisfaction. Lane counts alone cannot measure ergonomic balance.
- **Difficulty progression:** Easy/Normal/Hard are playable and sensibly differentiated; easier variants retain recognizable phrase/motif identity; added density does not overwhelm sparse songs or simply mirror every transient. Assess all three as charts, not just note counts.
- **Operational constraints:** elapsed time for warm/cold runs, peak memory, dependency/model download footprint, failures, deterministic repeatability under pinned versions, and licensing review.

Use a rubric with both quantitative and player judgments. Report per-song outcomes and failure modes; do not average away a bad subgroup. Establish acceptance thresholds before a full run with the parent/design owner. Do not call a tool winner or make quality claims until this evaluation is performed.

## Uncertainties and handoff

No test or subjective result says that pitch contour will outperform band evidence or current cycling on these particular tracks. PitchMelodia’s original paper is for predominant melody from polyphonic music, but the Essentia implementation page warns that implementation is adapted to monophonic signals; do not transfer the original task claim uncritically. Basic Pitch claims polyphonic transcription but says best on one instrument at a time; lead selection is unsolved. Harmonic/percussive decomposition is not source separation. License and dependency conclusions must be checked against exact pinned versions and bundled model assets before distribution. Parent/design owner should reconcile this research with scope, decide whether the draft’s band-lane proposal remains worth piloting, and authorize any future benchmark separately.
