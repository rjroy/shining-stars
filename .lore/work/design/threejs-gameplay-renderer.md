# Three.js gameplay renderer migration

This design moves the visible rhythm playfield from DOM/CSS into the existing Three.js renderer while preserving current gameplay, timing geometry, controls, city scene, and surrounding interface. It is a design artifact for parent review; implementation belongs in a later plan and implementation lane. It does not authorize a broad UI redesign or timing/game-rule changes.

## Current code and constraints

- `src/main.ts` owns one `requestAnimationFrame` loop. `frame()` calls `controller.update()`, whose render callback calls `renderSnapshot()`. That callback updates the DOM UI and then calls `scene.update(projectSceneState(snapshot, ...), snapshot.game.transportTime)`. `runAction`/`runPlaybackAction` only show busy state; `startOrRetry`, the Enter branches (Start, Resume, Results Restart), and UI button actions can all reach audio actions through separate paths. There is no renderer-availability gate or request epoch shared with renderer loss yet. Audio transport remains authoritative; do not add a scene-owned loop or another song clock.
- `src/scene.ts` owns one transparent, low-power `THREE.WebGLRenderer`, one full `.play-surface` canvas, a perspective city scene, its `ResizeObserver`, context-loss listener, and cleanup. It caps device pixel ratio at 1.5. `SceneRendererFactory` already provides a test seam, but its narrow renderer interface does not yet expose viewport, scissor, or explicit clear operations.
- `src/scene-state.ts` is the pure model-to-city-visual projection. It reads the active run difficulty and reduced-motion choice. Keep it separate from game rules and do not make it the owner of song time.
- `src/ui.ts` builds the page and currently paints the four lanes, lane keys, notes, hit line, timing bands/envelopes, and judgment feedback as DOM/CSS. It also owns Ready/Pause/Results/Error panels, difficulty selection, controls, and accessible status text. It measures only `.lane-board` for timing geometry, although the visible timing legend and feedback row sit after the board. Its mutable `lastFeedbackId`/`feedbackTime` pair is local to the UI and does not include a run/event generation; controller start, resume, pause, restart, and idle difficulty replacement clear feedback independently. The existing gameplay timing geometry comes from `src/note-projection.ts` and the canonical difficulty profiles.
- `src/styles.css` places the scene canvas behind the stage frame and UI. The current lane board is 4 columns; notes travel from 18% to 82% of the board height over `VISIBLE_NOTE_SECONDS = 2.4`, clamp at the hit line, and remain there while a Good judgment is still eligible. Timing envelopes are symmetric around a note/target; Good is the outer envelope and Perfect the smaller core.
- The current generated chart has 80 notes and allows Normal/Hard. At most 7 unresolved notes can be projected at once when counting the 2.4-second approach plus the largest currently allowed late grace (`150 ms Good + 200 ms input offset = 350 ms`). This is derived from the chart's timestamps and current allowed profiles, not a performance benchmark. Recompute capacity from each chart and its permitted profiles; never treat 7 as a global chart limit.

## Decision: one renderer, a second orthographic playfield pass

Keep the existing canvas, WebGL context, renderer, city scene, application loop, and scene lifecycle. Add a dedicated gameplay scene and an orthographic camera, rendered as a second pass over the complete stage-frame presentation with a narrower board scissor for the lane field.

1. Render the existing city scene once over the full `.play-surface` with the current perspective camera.
2. Convert the outer `.stage-frame` and inner `.lane-board` rectangles to renderer viewport coordinates, including host-relative position, WebGL's bottom-origin Y coordinate, and the renderer's existing pixel-ratio convention. Never use `.lane-board` alone as the whole gameplay viewport.
3. Set the outer stage-frame scissor, clear depth only in that region, then render a screen-space backing plane matching the current panel surface plus feedback/legend text at their measured rows. Switch to the board-local scissor, clear **depth only inside that scissor** (never color), and render lane rails, labels, hit line, targets, notes, and envelopes through a fixed orthographic camera. Restore the outer rectangle/renderer state before returning. These are two gameplay regions (outer stage frame and inner board); feedback does not need its own clipping rectangle because it is drawn in the outer region outside the board subpass. Neither pass clears color, so the city remains visible through the translucent GPU backing.
4. Keep the canvas transparent and behind HTML controls, menus, status panels, and results. Make the stage/frame/layout anchors transparent and remove their visible DOM lane/note/hit-line/feedback paint. The empty anchors exist only to preserve responsive geometry; they must not look like a second or fallback playfield.

### Backdrop and layer order

The current `.scene-canvas` is at z-index 0; `.stage-frame` is at z-index 1 with a `rgb(9 16 29 / 64%)` background, `.lane-board` paints `rgb(8 14 26 / 42%)`, and `.lane` paints translucent gradients and lane borders. Merely drawing gameplay into the existing canvas would leave that DOM paint over the meshes and dim them. Remove those opaque/translucent DOM backplates and lane strokes from the playfield. Keep the stage/frame/layout elements transparent over the canvas, with their borders and static text above it. Recreate the existing dark stage and lane shading as Three.js backdrop planes in the outer-stage and board subpasses, matching current CSS colors/opacities over the city rather than inventing a new panel treatment; draw rails, notes, bands, and feedback above those planes. Keep actual DOM menus, dialogs, controls, and results above the canvas with their current readable opaque surfaces and focus order. Do not raise the whole canvas above controls or make controls translucent to expose the scene.

The gameplay camera maps CSS pixels into a stable, screen-parallel coordinate system. If the board is `W × H` CSS pixels, lane centers are at `(i + 0.5)W/4`; note center Y is `(.18 + progress × .64)H`; the hit line is `.82H`. This preserves the current 18%–82% travel path without perspective changing the perceived timing windows. For the active profile's symmetric `±T` seconds, with travel distance `D = .64H` and approach duration `V = 2.4s`, the Good/Perfect band half-height is `T × D/V`, and each note envelope height is `2 × T × D/V`. The note and target receive the same projected geometry; late notes continue to clamp at the line. Do not change scoring, hit windows, offsets, transport, chart, or note travel time to make the renderer easier.

The scene pass must cover the whole visible gameplay presentation, not just `.lane-board`: current feedback and the timing-window legend are below that rectangle, while lane labels are inside it. Use the existing `.stage-frame` as the larger non-painting presentation anchor. Its outer scissor covers its complete content area, including board, timing legend, feedback row, and the surrounding stage panel. Add/cache a board-local content rectangle and feedback/legend baseline rectangles relative to that outer region. Render the stage substrate and feedback/legend labels in the outer pass; render lane rails, lane labels, notes, hit line, target bands, and envelopes only within the narrower board-local scissor. This two-region layout keeps labels below the board visible without allowing notes/envelopes to escape the lane field. Stage time/resource/mode readouts, input instructions, native controls, and accessible status text may remain DOM.

### Alternatives not selected

- **Put playfield meshes in the city perspective camera:** reject. Perspective depth and camera movement would alter note size and timing-window pixel scale, and make lane alignment depend on city-scene composition.
- **Create a second canvas/renderer:** reject. It adds another WebGL context, resize/disposal/context-loss path, layer ordering, and opportunity for clock/render desynchronization without a gameplay need. Scissoring the current renderer provides the same isolated camera while retaining one draw surface and lifecycle.
- **Keep DOM lanes as the visual fallback:** reject. The gameplay field must be rendered by Three.js in normal operation. DOM content is retained for semantics and controls, not as a parallel visible implementation.

## Rendering and ownership contracts

### Typed frame adapter

Keep the game model and controller authoritative. Add a narrow, pure projection boundary between the existing snapshot/chart inputs and the renderer rather than passing `ControllerSnapshot` through the Three.js scene or reading the DOM from render objects. The frame should contain only what the visual scene needs:

- the existing `SceneStateProjection` for city phase, intensity, transition, and reduced-motion behavior;
- active `game.difficulty`/profile, projected unresolved notes (IDs, lanes, progress/position), and the same Good/Perfect timing geometry derived from the profile;
- whether the note field is visible for the current lifecycle state, the current transport time, and the immutable judgment event (`eventId`, `runId`, `noteId`, quality, onset transport time);
- cached playfield layout dimensions supplied by the scene/layout observer, not a second time source.

Use `projectNotes` and `projectTimingWindowGeometry` as the existing pure projection seam, or extend them narrowly. The `game.difficulty` frozen into the current run is the only timing-profile source during that run; `selectedDifficulty` is only for the next run. Preserve `projectNotes`' existing overdue clamp and outcome filtering. Do not duplicate timing profile constants in the renderer.

`BrightvaleScene.update` should accept the projected frame and transport time or a single frame containing both. It performs the city and gameplay render passes in the same call. It owns no `requestAnimationFrame`, timer, wall clock, input handler, audio state, or scoring logic. UI panels, difficulty controls, Pause/Resume/Retry buttons, result copy, and audio/loading/error states remain native DOM. Main keeps the existing `D/F/J/K`, Escape, Enter, editable-target, audio, and focus semantics, but all playback entry routes must pass through the new renderer-availability guard described below; the current routing cannot remain unguarded.

### Presentation-region geometry

Use `.stage-frame` as the outer presentation anchor and `.lane-board` plus feedback/legend rows as child anchors. Convert each child rectangle relative to the existing `.play-surface` canvas, clip it to the canvas/host bounds, and cache CSS-pixel sizes/offsets when the stage frame, board, feedback rows, or host changes size/position. Do not use the board rectangle as the complete gameplay viewport: it omits the feedback and timing labels that are explicitly moving to Three.js. Do not read layout after DOM writes every RAF. The renderer uses one logical CSS-pixel coordinate system and the existing capped pixel ratio; convert coordinates to Three.js/WebGL viewport conventions exactly once, including bottom-origin Y and clipping.

### Stable GPU objects

Create lane rails, lane labels, hit line, hit pads, fixed Good/Perfect bands, note glyphs, note envelopes/cores, and visible judgment feedback as objects in the gameplay scene. Preserve the existing lane order, note silhouettes, color meaning, fixed hit-line position, and contrast hierarchy; use flat orthographic meshes/materials so the camera does not change their apparent size. Keep the existing city scenery and its role behind the rhythm field. This is a rendering migration, not the requested later redesign of the box-like note appearance.

Allocate geometry/materials and note slots when the scene/chart is created. Hide unused slots and update object transforms/visibility from each projected frame; do not create/dispose `BufferGeometry`, `Material`, or DOM note nodes per frame. A small pool sized from the chart's maximum projected unresolved-note overlap is sufficient for this chart (derived maximum 7); calculate the safe pool from chart timestamps plus the largest permitted Good window and input-offset bound when charts or allowed profiles change. Assert the projection never exceeds the prepared capacity. Instancing is a reasonable implementation if it simplifies repeated flat lane/note geometry, but is not a requirement by itself; prefer the simplest pool that preserves distinct note colors and envelopes.

### Text and feedback

Visible D/F/J/K lane labels, HIT marker, timing-window labels, and the current Perfect/Good/neutral feedback move into the gameplay render pass. Reuse the current copy and visual hierarchy. A small pre-rendered glyph atlas/CanvasTexture with the existing monospace/system fallbacks is an acceptable first implementation; do not download fonts, add a font asset pipeline, or allocate a text texture every frame. Update dynamic text only when its value changes.

Keep an equivalent visually-hidden, polite screen-reader status for judgment feedback and concise keyboard/lane instructions in the DOM. Announce judgment changes, not note positions on every frame. Keep accessible labels on visible native controls. The canvas is `aria-hidden`; it is not a replacement for the keyboard control semantics.

The current UI shows a judgment for 0.65 seconds of `game.transportTime`, not 0.65 seconds of wall time. The scene adapter needs an explicit immutable feedback event; do not reproduce the UI's mutable `lastFeedbackId`/`feedbackTime` tracker or infer event onset from whichever render frame first observes a non-null result.

**Source the feedback event in the controller**, where the press is judged and its transport timestamp is known. Extend `ControllerSnapshot` with an immutable feedback event containing a monotonically unique `eventId`, `runId`, `noteId`, `quality`, and `onsetTransportTime` equal to the exact transport time passed to `game.press`. Increment `runId` whenever the controller installs a fresh game; increment `eventId` whenever a new press produces feedback, even when the same chart `noteId`/quality recurs in a later run. Clear the event to `null` on start/count-in, pause, resume/count-in, restart, idle difficulty replacement, terminal results, renderer-failure cancellation, and disposal. This small controller metadata change avoids a main/UI mirror clock and prevents stale feedback or same-note-ID suppression across recreated runs.

Render feedback only while the active run is playing and `transportTime - onsetTransportTime < 0.65s`; use transport/game time, never wall time. Pause and count-in do not advance that age, but the controller's existing clear-to-null transitions hide the feedback during those states. Renderer loss also pauses/clears it; recreating the scene must not resurrect the previous event. `eventId` supports texture/object updates only when the event changes; `runId` makes the reset contract explicit and testable.

## Layout, responsive behavior, and render cost

Keep `.lane-board` or a renamed equivalent as a non-painting DOM layout anchor so the current stage sizing, mobile layout, and surrounding controls remain intact. Observe the playfield and the containing stage for size changes; cache its rectangle relative to `.play-surface` and update the gameplay camera/viewport on resize. Observe ancestors that can change the anchor's position, not only its own size. Use the current resize fallback when `ResizeObserver` is unavailable. Do not call `getBoundingClientRect()` after UI DOM writes on every render frame; layout reads belong in the resize/measurement path. Update renderer pixel ratio on browser zoom/device-pixel-ratio changes without multiplying CSS coordinates by the ratio twice.

Use the same current render cadence and snapshot clock for both render passes. The city and playfield may share one frame's draw call scheduling, but the city scene must not start or stop gameplay visuals independently. Keep the current capped pixel ratio and low-power renderer settings unless browser evidence shows a concrete problem. Do not claim a frame-time target or performance win before profiling; the derived current-chart overlap is 7 visible/unresolved notes, not proof of GPU performance.

Reduced motion continues to suppress the city pulses, wind travel, and camera push through `projectSceneState`. Note motion remains essential to the rhythm input and is not silently replaced by static positions. No new decorative motion or effect framework is part of this migration.

## Failure, recovery, and lifecycle

The existing scene currently removes its canvas on renderer creation/render failure and calls a generic fallback callback; the current UI says the song and DOM rhythm lanes continue. Replace that contract. App-level renderer availability is a hard gate on playback, not merely a presentation flag.

- Maintain an app-owned `rendererAvailability` state (`unavailable`, `ready`, `recovering`) and a monotonically increasing `playbackIntentEpoch`. Start with availability `unavailable`; set it to `ready` only after scene/renderer creation and the first successful required render. A missing WebGL context, context loss, failed draw/resize, or active recovery makes it unavailable synchronously.
- Guard every path that can begin/rebegin audio **before invoking the controller**: visible Start, Resume, Results Restart, audio Retry (`startOrRetry`), Enter on Ready, Enter while paused, Enter at Results, and any accessible/key shortcut path. Disabled buttons are feedback, not the guard. Keep Pause available; it must also be invoked automatically on renderer failure.
- While unavailable/recovering, also ignore D/F/J/K gameplay input at the app boundary and clear held keys through the controller cancellation path. Do not accept hits while notes are invisible; normal keyboard routing resumes only after a successful renderer retry.
- When a renderer becomes unavailable, synchronously set unavailable, increment `playbackIntentEpoch`, detach the scene, show a renderer-specific error and Retry 3D view action, then call the controller's pause/cancel path. The controller's existing action/control epoch already prevents a pending `start()` from scheduling after pause; retain that protection and add the app epoch/availability check before and after each awaited load/start/resume/restart action. If an audio load resolves after the renderer epoch changed, do not start or resume it; ensure the controller is paused and the scene error remains visible. This covers a context loss during a pending load, not just loss during an already-playing frame.
- At startup, block audio until the first successful renderer initialization. During recovery, block Start, Resume, Restart, and audio Retry regardless of whether audio is `ready`, `loading`, `paused`, `results`, or `error`. Renderer Retry is a separate action and never calls `controller.restart()`. If audio has its own error after renderer recovery, then expose the normal audio Retry while the renderer is ready.
- Renderer Retry moves through `recovering`, recreates the scene on the existing host, validates a successful frame, then sets `ready`. It never resumes audio automatically. If the prior run was interrupted, return to Pause and require explicit Resume; if no run began, return to Ready; if audio is still in error, preserve the audio error/retry after renderer readiness. Failed retry returns to `unavailable` with a distinct recoverable message.
- Reflect app-owned renderer availability in the visible native controls as well as enforcing the main-layer guard. While unavailable/recovering, Start/Resume/Restart and audio Retry are disabled and the renderer error/Retry 3D view is visible; Pause remains available. Keep renderer and audio errors as separate state: renderer Retry must not erase an audio error, discard frozen results, or change the audio/controller snapshot. After renderer recovery, show the appropriate Ready/Pause/Results/audio-error surface for the preserved model/transport state. Busy-state cleanup after a stale action must not overwrite a newer renderer-unavailable state.
- Ensure failure handling does not recursively publish/render while the scene is being torn down. The application owner detaches the failed renderer and invalidates the intent epoch before synchronously canceling audio. Add one narrow controller operation for this boundary (for example, `pauseWithoutPublishing()`): it invalidates the controller's pending action epoch, clears held keys/feedback, pauses audio, catches up the game to the paused transport position, and returns a snapshot without invoking the render callback. After `scene.update` unwinds, `main` applies that returned snapshot to the DOM. This prevents an async `start()` from scheduling after the loss and avoids re-entering `controller.publish()` from inside its own render callback. Make the transition one-shot and safe whether failure occurs during construction, first render, `update`, or resize. Late async completion must not clear a newer renderer error or enable playback.
- `destroy()` removes resize/context listeners, disposes every scene/geometry/material/texture, removes the canvas, and cancels any scheduled recovery work. Main remains the sole owner of app disposal and audio/controller disposal.

## Accessibility and visual parity

Keep the present composition, colors, stage scale, lane order, keyboard labels, hit-line origin, note approach/clamp, Good/Perfect inclusion, feedback words, panel behavior, responsive breakpoints, and city/background layering. Avoid adding a second decorative lane frame or rebuilding the UI around new boxes. DOM panel and controls must remain above the transparent WebGL canvas and keep their current focus behavior. The game canvas is pointer-transparent; no new pointer, touch, or mobile control contract is implied.

Use both shape/treatment and color to distinguish Good from Perfect (outer Good boundary, nested Perfect core) so the distinction does not depend on lane color alone. Preserve narrow-layout readability and true timing geometry; if a thin Hard window needs help, increase outline contrast rather than enlarging the accepted region. Keep the existing screen-reader feedback status even though its visual counterpart is rendered by Three.js.

## Test and browser evidence expected in the implementation lane

1. Retain deterministic tests for `projectNotes`, timing windows, active frozen profile, clamped late notes, and exact projection endpoints. Add unit tests for the pure gameplay-frame adapter: only active-run difficulty, correct note progress/lane, matching note/target geometry, Good/Perfect nesting, visibility by lifecycle state, and no duplicate DOM gameplay objects.
2. Test controller feedback metadata: event onset equals the exact transport time passed to `game.press`; `eventId` changes for each event; `runId` changes on fresh-game installation; the same `noteId`/quality in a later run is a new event; null clears it on start, pause, resume/count-in, restart, idle difficulty replacement, results, renderer loss, and dispose; the 0.65-second lifetime uses transport time and does not age during a pause. Scene recreation must not replay the prior event.
3. Test playback gating through every route while renderer status is unavailable/recovering: Start, Resume, Results Restart, audio Retry, Enter on Ready/Paused/Results, and any direct action callback must not call audio/controller playback. D/F/J/K key events must not judge notes or change feedback while unavailable. Also test renderer loss while `start()`/`resume()`/audio Retry is awaiting load; resolving the stale promise must not schedule audio, clear the scene error, or enable input. Test initial renderer failure, successful Retry, failed Retry, and renderer readiness before audio Retry after an audio error.
4. Extend the existing `SceneRendererFactory` seam with the smallest needed viewport/scissor/clear API. Tests should assert pass order (full city render; depth-only clear, transparent stage backing, and feedback/legend in the outer stage-frame scissor; depth-only clear and orthographic lane render in the nested board scissor), clipping/coordinate conversion, cached stage-frame/board/feedback layout, frame reuse, stable object/pool count, no per-frame geometry/material/DOM allocation, and one-time disposal on destroy/context loss.
5. Exercise the actual renderer in a browser with WebGL/SwiftShader when already available; do not install a browser or dependency. Capture desktop and narrow screenshots for Normal and Hard and inspect actual rendered target and note-envelope bounds. Verify Hard/Normal is 2/3 for both Good and Perfect at the same runway scale; responsive dimensions change with measured travel distance. Verify the stage/frame opacity does not tint the gameplay pass, panels/controls still cover the canvas, and no visible DOM note/lane/hit-line/band/envelope/feedback duplicates remain.
6. In browser, exercise keyboard hit/miss feedback, pause/resume/count-in, restart, reduced motion, audio stop when WebGL context is lost, pending-load cancellation on loss, failed renderer Retry, successful renderer Retry, gated audio Retry, and no automatic audio resume. Confirm context listeners/resources are disposed. Avoid claiming precision victory: browser automation cannot establish correct musical alignment; do not retune note timing in this renderer work.
7. Run the existing test, typecheck, lint, format, build, chart-check, and Python chart workflow gates. Report actual browser/device availability, any skipped verification, and profiling results without inventing timing/performance claims.

## Material choices to keep visible in review

- **Chosen:** one existing renderer/canvas with a scissored orthographic playfield pass. This limits synchronization and context ownership while preserving the city perspective scene.
- **Chosen:** retain DOM only for controls, panels, result/settings content, and nonvisual accessibility semantics; no visible DOM gameplay fallback.
- **Chosen:** flat, screen-parallel 3D geometry and current appearance for parity, with one transport-clock snapshot and no added scene loop.
- **Chosen:** use the full stage frame as the outer presentation region and the lane board as a nested clip; draw feedback/legend in the outer region below the board. Preserve stage shading with GPU backing, not an opaque DOM layer over the canvas.
- **Chosen:** gate all audio-starting actions on app-owned renderer readiness; a renderer recovery is a separate step from audio Retry and never resumes playback itself.
- **Chosen:** controller-owned immutable feedback event metadata (`eventId`, `runId`, note/quality, exact onset transport time), rather than per-frame UI identity/time bookkeeping.
- **Still implementation details:** whether a small note pool or `InstancedMesh` is the simpler fit, and which local canvas glyph-atlas layout produces the most legible labels. Decide from the current chart and measured browser output, not from a new asset/font pipeline.
- **Deferred fast follow — general refactor:** after the rendering migration, diagnose remaining `main`/`scene`/`ui` ownership coupling first, then scope a cleanup only where the diagnosis identifies real cost. Do not combine an unbounded architectural refactor with this migration.
- **Deferred fast follow — note visual redesign:** the user dislikes the current box-like note treatment. Revisit note shapes/materials as a separate visual design task after GPU parity is established; do not use this migration to sneak in a replacement visual world.
