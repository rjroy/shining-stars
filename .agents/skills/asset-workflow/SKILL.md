# Asset workflow

The user is the **visual director**, not the artist or operator. The agent owns the brief, concept-art request, modeling, iteration, evidence, and integration work. Ask the user for direction and explicit decisions; do not make them operate Blender or produce the asset. These instructions describe how to execute asset work; they do not themselves authorize it. The current skill-authoring request authorizes documentation only, not concept generation, modeling, integration, or asset creation. For future asset work, obtain task authorization and satisfy each approval gate below.

## Approval gates — never collapse or infer them

1. **Description approval.** Write a concise asset brief and obtain explicit approval of its purpose, silhouette, style, gameplay/readability needs, and constraints. A general request to make an asset is not approval of a proposed description.
2. **Concept art.** After the brief is approved, use the `concept-art` skill to request a concept. Keep the actual generated image and record its path. Present it for review; do not proceed to modeling until the user explicitly approves that concept.
3. **Model and critique loop.** Use `blender-model` and `blender-visualize` to create the model and make disposable, reproducible previews that show the actual model for concept comparison. Open and inspect them; they are geometry-review evidence, not the final product or runtime-fidelity proof. Judge model approval on silhouette, proportion, construction, detail, topology, and visible geometry flaws using neutral or restrained views. Do not require concept-lighting reproduction or let emission, bloom, exposure, lighting, tone mapping, reflections, or final material presentation alone block geometry approval or trigger modeling iterations. Preserve meaningful material assignments/separation and export-relevant structure; report presentation differences honestly. Assess final appearance separately during runtime integration. Bring focused evidence/questions to the user; do not ask them to model or run the loop. Avoid toy-like substitutes. If convincing modeling is not possible, explain why and ask for direction. Iterate in bounded batches; if geometry stops materially improving, pause with evidence and remaining gaps. Request explicit **model approval** against geometry evidence; concept approval is not model approval.
4. **Runtime integration.** Only after model approval, integrate the approved export into the runtime. Keep the editable source and build/export process reproducible. Present runtime evidence and request separate explicit **integration approval**. Neither prior approval implies this one.

## Modeling-agent routing

For authorized Blender construction and geometry critique, use the custom `@modeler-sol` and `@modeler-astra` agents configured in the user's oh-my-opencode-slim setup. Route ordinary or moderately complex structured/environment assets—especially highways, endcaps, and framing—to `@modeler-sol`. Route significantly complex anatomy, characters, intricate hero architecture, and crowd/background-castle work to `@modeler-astra`; escalate to Astra if Sol cannot meet the approved form quality. The designer retains concept and art direction; modelers execute approved descriptions/concepts and critique actual geometry. This routing does not grant modeling permission: satisfy the approval gates above, preserve source ownership, and do not infer runtime integration authorization. If either named agent or its configured model is unavailable, report that blocker and ask how to proceed; never silently substitute Fixer, Luna, or another modeler.

If approval is withheld or requested changes, return to the relevant earlier gate. Reset approvals proportionally: a material change to the brief requires renewed description approval and a new/reviewed concept; a material concept change requires renewed concept approval before modeling resumes. Minor changes that do not alter approved intent need not restart unrelated gates; record the rationale and version. Preserve prior approved versions and approval records in the package or an authorized archive as appropriate; permanent numbered directories are not required. Never treat silence, a render, or a broad initial request as approval.

## Maintained handoff and storage

Use one stable, relocatable asset directory. Keep the current approved editable `.blend`, its current deterministic generator, only genuinely reusable validation/preview scripts, the approved brief/concept, and a short README. If a gate is pending, identify the current file as a candidate and state its status. Record provenance/permissions, separate approval decisions and revision history, Blender version and reproduction steps, orientation/scale, measured bounds, and known limitations there. Use stable filenames; identify revisions in the README/approval history rather than accumulating permanent numbered directories. Keep runtime exports separate and add them only at integration.

During active iteration, never overwrite the approved/current source: use temporary working copies and preserve the prior version until its replacement is regenerated and checked. Promote reviewed work to stable package paths when appropriate; archive earlier work outside the maintained package when useful. Keep the approved concept and evidence that supports approval, but do not accumulate every log, failed attempt, per-iteration render, regenerated copy, duplicate script, or redundant manifest in the package. Archive or ignore scratch outputs. Do not blindly delete approval records or the only copy of approved evidence; before cleanup, verify a durable copy and provenance record exist and archival/removal is authorized. Native image-tool staging need not be retained after the approved image has a verified durable copy and recorded provenance.

Choose Git, Git LFS, or external storage based on file size and repository policy; agree on storage for large assets and explain clone/backup consequences. Do not categorically exclude binaries, install LFS, or commit files without authorization. Make the maintained package self-contained and relocatable: scripts must not depend on session-specific `/tmp` files or machine-local scratch paths. Verify regeneration from the packaged source before calling it reproducible.

Do not invent approved polygon, texture, draw-call, memory, or other performance budgets. Label unknown values unknown; document material separation/export needs without treating model-stage presentation as final runtime appearance. Preserve the separate description, concept, model, and integration approval gates.
